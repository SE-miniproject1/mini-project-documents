# Deviations Log

Where the implementation differs from the SRS, the SAD or the Test Plan, and why. Entries are added as the work is done. Each says what to change in the document, or confirms that the document is still right.

| ID | Story | Document and section | What the document says | What was built or found | Action |
|---|---|---|---|---|---|
| D-01 | US-02 | Test Plan, SV-01 test data | Lists `Password123!` as a password on the compromised list | It is not on Django's common-password list of 19,640 entries. `password1!` is, and it passes every other rule, so it isolates the list check | Test Plan corrected in this change |
| D-02 | US-02 | SRS 3.1 UI-6 screen inventory | Lists "Login and Password Reset" | A password change screen was added, because NFR-SEC11 requires sessions to end on password change and a user needs a way to do that | Add "Change Password" to the screen inventory |
| D-03 | US-02 | SRS NFR-SEC1 | Authenticate by username and password | Sign-in is by username. Email is also required and unique, because NFR-SEC4 emails the holder on lockout and the reset flow needs it | None, consistent with the SRS |
| D-04 | US-02 | SRS NFR-SEC4 | Lock for 15 minutes after 5 failures and notify the holder | The sign-in form says the account is locked and for how long when the username exists. This helps a real user and tells an attacker the username is valid. Failed attempts on unknown usernames get the normal generic message | Accepted trade-off. Revisit if the security review objects |
| D-05 | US-03 | SRS 3.1 UI-5 | Irreversible actions need a confirmation dialog naming the record | Not built in this story. No irreversible action exists yet. It is built with the first one (US-14 manual discard, US-19 issue) | Tracked against those stories |
| D-06 | US-03 | SRS 3.1 UI-3 | Alt+N new record, Alt+S save, Alt+F search, Escape cancel | Implemented with the key's physical position, so it works on any layout including macOS, where Alt+letter types a different character. Pages opt in with `data-shortcut="new|save|search|cancel"` | None, behaviour matches the SRS |
| D-07 | US-03 | SRS 3.1 UI-6 | One home screen per role | A single home page lists the screens the role may use. The menu is generated from one registry in `core/navigation.py` and only shows a link once its page exists | None |
| D-08 | US-04 | SRS Appendix B.1 | Lists the donor fields | Two fields were added: `user`, which links the donor to its sign-in account, and `deferral_review_date`, which REQ-8 needs to clear a deferral automatically. Both are needed and neither contradicts the layout | Add both to Appendix B.1 and the ER diagram |
| D-09 | US-04 | SRS 5.1.2 sequence 1 | Registration creates the donor record | Registration also creates the donor's sign-in account in the same transaction, with the donor ID as the username. The password is chosen on the registration form | Mention the account in sequence 1 |
| D-10 | US-04 | SRS REQ-2 | Identifier of the form DNR followed by 8 digits | Numbers come from a database counter starting at 10000001, matching the Test Plan seed data. A rejected registration does not use up a number | None |
| D-11 | US-07 | SRS REQ-6, REQ-8 | A donor failing a criterion is deferred with a review date | The SRS gives no review date for weight, haemoglobin or blood pressure. 30 days is used, held in `BBMS_ELIGIBILITY`. A donor failing only the interval is reviewed on the next eligible date. Under 18 is reviewed on the 18th birthday | Ask faculty or the blood bank for the intended figure, then state it in REQ-8 |
| D-12 | US-07 | SRS REQ-6 | Lists age 18 to 65 as an eligibility criterion | A donor over 65 is marked Permanently Deferred, because age cannot recover. The SRS lists only Temporary and Permanent without saying which applies | State this in REQ-6 |
| D-13 | US-07 | SRS Appendix B and ER diagram | No entity for a screening visit | `DonorScreening` was added to keep the measurements, outcome and reviewer for each visit | Add to Appendix B and the ER diagram |
| D-14 | US-07 | SRS REQ-46, REQ-6 | Thresholds are configurable by an administrator | Thresholds live in `BBMS_ELIGIBILITY` in settings until US-26 builds the configuration screen. A system check refuses an interval below 90 days (BR-2) | Resolved by US-26 |
| D-15 | US-08 | SRS REQ-8 | A temporary deferral clears automatically once its review date has passed | The nightly job re-checks only age and the donation interval. Weight and haemoglobin are not re-checked, because an old reading says nothing about today. The donor returns to Eligible and is checked again at screening. Re-using the old reading would either defer the donor for ever or pass them without a measurement | State in REQ-8 that clearing does not replace screening |
| D-16 | US-08 | SRS REQ-7, NFR-S5 | Collection is blocked when the donor is not Eligible | The guard also checks the dates, so a stale status cannot allow a donor to be bled inside the 90-day interval | None, this makes NFR-S5 hold in more cases |
| D-17 | US-08 | SRS REQ-8 | The donor's next eligible date is shown | A donation sets the donor to Temporarily Deferred with the reason "Donation interval not elapsed" until the next eligible date, so the dashboard, the search screen and the nightly job all use one mechanism | None |
| D-18 | US-10 | SRS REQ-11, REQ-16 | A unit moves between six statuses | The SRS names the statuses but not every legal move. The moves are Quarantined to Available, Discarded or Expired. Available to Reserved, Expired or Discarded. Reserved to Issued, Available, Expired or Discarded. Expired to Discarded. Issued and Discarded are final | Add the transition table to REQ-16 or the SAD |
| D-19 | US-10 | SAD 3.4 Inventory Management | Every transition writes an audit record in the same transaction | Each transition sends a `unit_status_changed` signal inside the transaction. The audit store (US-12, Sprint 2) subscribes to it, and a failing subscriber rolls the change back | Closed by US-12 |
| D-20 | US-10 | SAD 3.5, NFR-S4 | Row-level lock so two staff cannot both act on a unit | `transition_to` locks the row and refuses a stale copy. SQLite ignores the lock, which is fine for development, and PostgreSQL enforces it | Verify on PostgreSQL in US-27 |
| D-21 | US-10 | SRS REQ-15 | Component separation creates child units | A unit can only be created Quarantined, so child units start there and are moved on by US-16 | Revisit in US-16 |
| D-22 | US-09 | SRS REQ-9 | Volume is recorded in millilitres | No valid range is given. 200 to 600 ml is enforced to catch typing mistakes. A whole blood donation is normally 350 to 450 ml | Confirm the range with the blood bank and state it in REQ-9 |
| D-23 | US-09 | SRS REQ-9, REQ-36 | The site is the centre or a named camp | The site is free text defaulting to "Centre" until camps exist. US-22 links it to a camp | Closed by US-22 |
| D-24 | US-09 | SRS 5.2.2 sequence 2 | An aborted collection discards the unit with reason Aborted Collection and defers the donor | No requirement covers it, so it is not built. It would need a REQ and a Test Plan case | Add a requirement or drop the sequence |
| D-25 | US-09 | SRS REQ-10 | A scannable barcode on the unit label | Code 128, rendered as SVG with the `python-barcode` package. The label shows the unit and never the donor | None |
| D-26 | US-11 | SRS REQ-14 | A Reactive result discards the unit when the unit is released | A Reactive result discards the unit as soon as it is recorded, even if the other tests are still missing, so a known-reactive unit never waits in quarantine. Clear results can be entered over several visits and the unit is only released on request | State "when recorded" in REQ-14 |
| D-27 | US-11 | SRS Appendix B.3 | Test results have a Tested By field | Results are recorded once and cannot be edited, because a wrongly entered Non-Reactive result would let an unsafe unit through. There is no correction screen. A wrong Reactive result discards the unit and needs a new unit | Decide with the blood bank how corrections should work |
| D-28 | US-11 | SRS REQ-13, NFR-S2 | Release moves the unit to Available | A unit that has already passed its expiry date while waiting for results is marked Expired instead of being released | State in REQ-13 |
| D-29 | US-11 | SRS REQ-16 | A storage location per unit | A released unit is shelved at `BBMS_DEFAULT_STORAGE_LOCATION` (FRIDGE-A1). Moving it is the transfer feature (REQ-21, US-14) | Closed by US-14 |
| D-30 | US-13 | SRS REQ-17, NFR-P5 | The stock view reflects any committed change within 5 seconds | Counts are computed from the database on every request, never cached. The page also refreshes its live panel every 5 seconds by fetching a fragment. Without scripting the data is still current on every load | None |
| D-31 | US-13 | SRS REQ-17 | Available units are counted by blood group and component | Units past their expiry date are left out even if the nightly job has not yet marked them Expired, so the console and the allocation check can never disagree (NFR-S2) | None |
| D-32 | US-13 | SRS 3.1 UI-6 | The inventory console shows stock by group, component, status and expiry | This story shows stock by group and component, counts by status, and the units waiting for results. Filters, expiry buckets, near-expiry flags and transfers are US-14 and US-15 | Closed by US-14 and US-15 |
| D-33 | US-13 | Test Plan section 6 | A deterministic seed fixture with `staff01`, `hosp01`, `admin01` and donor `DNR10000001` | `manage.py seed_demo` creates those accounts and 10 donors with fixed IDs, plus units in every state, through the real services. | D-34 | US-12 | SRS NFR-SEC10 | Each entry carries the source address | The address is taken from `REMOTE_ADDR`. Behind Nginx that is the proxy's address unless the proxy is set up to pass the client's real one. Settle this when deploying | Add to the deployment guide (US-29) |
| D-35 | US-12 | SRS REQ-23, SEC-OBJ-2 | Audit records cannot be edited or deleted through any application function | That is enforced in the application: model and queryset refuse changes, the admin is read only, and a test forbids code from trying. | D-36 | US-12 | SRS NFR-SEC10 | Entries for authentication events, authorisation failures, status transitions and configuration changes | Sign-in, sign-out, failed sign-in, lockout, authorisation failure and unit status change are recorded now.
